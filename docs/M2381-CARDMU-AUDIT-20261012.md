## 4. 「手修 tar 顶翻 /lib」嫌疑证伪（AGENTS ② 挂案，本审计收口）

### 4.1 时间线修正
v1 的 /lib 是干净软链（§2）。此前 spot84e 看到的「/lib 真目录 + meizu 固件
平行树」是 **v2/v3 重建轮**（固件段改无条件叠加后才引入 tar 解包，顶翻发生在
构建侧），不是 v1。v1 的固件问题 = ath12k 短路（apk 压根没解），与顶翻无关。

### 4.2 tar 语义沙箱实测（本日实锤）
```
sandbox: lib -> usr/lib 软链 + tar -xf firmware-meizu-meizu20-1-r3.apk
结果:    lib 被顶成真目录（mtime = apk 内部时间 10-11 08:52）
         固件 100% 落平行树 /lib/firmware，/usr/lib/firmware meizu 件 = 0
```
apk 顶层条目 = `lib/`（目录项在档）——GNU tar 遇目录项默认先移除同名软链再建
真目录，与 build v2/v3 事故同构。**推论：手修 (c) 若在设备上用了
`tar -C /`，设备 /lib 必被顶翻，且固件实际没进 /usr/lib/firmware（修了个
寂寞）**；若走暂存+rsync 则安全。设备态已不可考，何法无档——但见 §4.3，
两种情况都不拦本次事故。

### 4.3 为什么顶翻也打不死内核启动（模块图谱判决）
r84 内核（#85）modules.builtin 内建判定：

- **内建**：msm.ko（DRM+adreno 全家）、**panel-boe-meizu20.ko（本机面板）**、

  gadget 全链）、sdhci-msm、msm_serial、backlight

kmod 硬编码 `/lib/modules`（strings 实锤）→ /lib 被顶 = 模块全断 = WiFi/触屏/
audio 死 + femto 缺导致 NCM 实枚举死 = **「USB/WiFi 全无」吻合**；但显示链

## 10. 对照实验收官：撕裂写归因定谳（2026-10-12 中午）

**实验**：同一镜像 4d9b179b（VERIFY 全绿），两次刷写入设备——

| 刷写轮 | 刷后重启方式 | fs 现态 | Vulkan JSON | gamescope |
|---|---|---|---|---|
| v4（0c752770，脚本刷） | ABL 僵死 → 用户长按电源强启 | clean with errors | 撕 11-13 个 | SIGABRT → 切 KDE |
| 固化盘（4d9b179b，脚本刷） | ABL 僵死 → 用户长按电源强启 | clean with errors | 撕 13 个（同清单） | SIGABRT → 切 KDE |
| 固化盘（4d9b179b，用户手动刷） | 手动刷 + 正常重启 | **clean** | **0 撕** | **正常会话** |

**判决**：
- **镜像无罪**（宿主逐字节验证：13 个 aarch64 JSON 与 base 全同 + e2fsck 元数据
  干净；目录块校验和属 ext4 元数据，e2fsck 会查，宿主通过 = 伤不可能是镜像自带）。
- **fastboot 刷写无罪**（本轮手动刷全绿）。
- **病根 = Mu ABL fastboot 命令环在大体积 userdata 刷写后僵死**（set_active/
  getvar/reboot 全部假应答，两轮复现）→ 操作者被迫长按电源强启 → UFS 写缓存
  丢尾巴 → 撕裂写恰好落在 /usr/share/vulkan JSON 群（base 构建期同批写入、物理
  相邻，一撕一串，两次清单一致即此故）。
- **规避 SOP**：刷完 userdata 后避免强启——`fastboot reboot` 重发 →
  `fastboot continue`（Mu 若支持 = 优雅继续启动）→ 实在最后才强启；强启后
  首启必跑 post-flash-health.sh（Vulkan Invalid JSON 计数 = 数据块健康代理）。
- **待外发**：ABL 僵态 bug 整理给 nura（复现步骤：fastboot flash userdata
  14G sparse 17 块 → set_active 假应答挂 6min+ → getvar/reboot 无应答 →
  强启后分区撕裂写；对照正常重启无伤）。
