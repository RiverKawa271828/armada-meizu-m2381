## 4. 「手修 tar 顶翻 /lib」嫌疑证伪（AGENTS ② 挂案，本审计收口）

### 4.1 时间线修正
v1 的 /lib 是干净软链（§2）。此前 spot84e 看到的「/lib 真目录 + meizu 固件
平行树」是 **v2/v3 重建轮**（固件段改无条件叠加后才引入 tar 解包，顶翻发生在
构建侧），不是 v1。v1 的固件问题 = ath12k 短路（apk 压根没解），与顶翻无关。

### 4.2 tar 语义沙箱实测（本日实锤）
```
sandbox: lib -> usr/lib 软链 + tar -xf firmware-meizu-meizu20-1-r3.apk
结果:    lib 被顶成真目录（mtime = apk 内部时间 10-11 08:52）
         固件 100% 落平行树 /lib/firmware，/usr/lib/firmware meizu 件 = 0
```
apk 顶层条目 = `lib/`（目录项在档）——GNU tar 遇目录项默认先移除同名软链再建
真目录，与 build v2/v3 事故同构。**推论：手修 (c) 若在设备上用了
`tar -C /`，设备 /lib 必被顶翻，且固件实际没进 /usr/lib/firmware（修了个
寂寞）**；若走暂存+rsync 则安全。设备态已不可考，何法无档——但见 §4.3，
两种情况都不拦本次事故。

### 4.3 为什么顶翻也打不死内核启动（模块图谱判决）
r84 内核（#85）modules.builtin 内建判定：

- **内建**：msm.ko（DRM+adreno 全家）、**panel-boe-meizu20.ko（本机面板）**、
  dwc3-qcom、phy-qcom-qmp-{combo,usb}、**libcomposite、usb_f_ncm**（NCM
  gadget 全链）、sdhci-msm、msm_serial、backlight
- **模块**（modprobe 断供才死）：ath12k（WiFi）、goodix_berlin（触屏）、
  phy-qcom-snps-femto-v2（HS USB2 PHY，NCM 实枚举走它）、audio/uhid/uinput 等

kmod 硬编码 `/lib/modules`（strings 实锤）→ /lib 被顶 = 模块全断 = WiFi/触屏/
audio 死 + femto 缺导致 NCM 实枚举死 = **「USB/WiFi 全无」吻合**；但显示链
与内核本体全内建 → 系统会起、屏幕会亮（gamescope/steam 会话是纯用户态），
**与「停在 Mu、内核不起」不符**。⇒ **该嫌疑从「事故主嫌」降级为「已排除」**
（若真发生过，它是次生 bug 而非死因；v4 构建侧已根治，不复现）。

## 5. 剩余活机制与「停 Mu」症状力学

「停在 Mu logo + USB/WiFi 全无」的两种成立路径（用户态会话都起不来的形态）：

- **路径 X：内核根本没跑/极早死**——ABL 侧问题（GPT 属性/槽位态）。
- **路径 Y：内核跑了但 root 挂载失败 → panic**——ESP cmdline 若带 quiet
  （fbcon 不出字），面板停在 ABL 交接的 splash = 视觉上就是「停在 Mu」；
  内建 msm 接管显示管线但 quiet 下无输出可画。fs 写伤（growfs 期中断/硬复位）
  走这条。

活机制对应：

| # | 机制 | 证据状态 | 实证窗口 |
|---|---|---|---|
| A | 刷后 fs 写伤（growfs/boot#1-#2 期硬复位或断电类中断；05:20:51 断连时点在案） | 无法事后取证（盘被 nura 覆盖）；as-built 镜像已五遍零错 | 刷后即时 ext4 健康采样（§6-3） |
| B | qbootctl -m GPT 属性写坏（boot#2 时点） | 无法事后取证；唯一 GPT 写者 + 上轮「重启落 fastboot」同域前科 | 刷后首启先读 `qbootctl -h` 槽位态再谈别的（§6-2） |
| C | 电池/供电（05:20:51 拔线后电池态） | 远端不可证伪；nura 复刷全程插线 | 刷写全程插线 + 冒烟时看 power supply 读数 |

变量收敛逻辑仍成立（同启动链彼侧一遍过），但「我方 userdata」要再拆一层：
**不是镜像 as-built 有病（本审计无罪判决），是「刷后首启写入态」或「刷写/
供电外部条件」有病。**
